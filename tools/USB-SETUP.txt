=====================================================================
  ALS Inventory - Hardware Audit USB: FULL SETUP (new pen drive)
=====================================================================
Everything needed to set up the audit + data wipe on a fresh USB stick.

THE STICK IN USE IS THE UBUNTU STICK (Secure Boot capable, graphical
kiosk): build it with UBUNTU-STICK.md, fill audit.conf from section C
here, wipe as in section E, and rebuild its layer once as in section H.
Sections A, D and G describe the OLD SystemRescue stick, which is no
longer in use (owner decision D41); they are kept for reference only.
SystemRescue commands are typed at the  [root@sysrescue ~]#  prompt.

What ends up on the USB (in the ROOT of the stick):
   hardware-audit.sh      the audit + wipe engine
   gui\                   the kiosk (Ubuntu stick)
   audit.conf             settings (server, login, Wi-Fi, admin PIN)
   autorun/autorun        SystemRescue only - inert on Ubuntu


---------------------------------------------------------------------
  A) MAKE THE SYSTEMRESCUE USB   (once - OLD stick, reference only)
---------------------------------------------------------------------
1. Download the SystemRescue ISO from https://www.system-rescue.org
2. Write it to an 8GB+ USB stick with Rufus (Windows), Ventoy, or
   balenaEtcher.


---------------------------------------------------------------------
  B) COPY THE FILES ONTO THE USB   (on Windows)
---------------------------------------------------------------------
1. Open PowerShell in this project folder:
      C:\Users\PC\Desktop\Als_Inventory_Software
2. Sync the tools onto the stick (E = the stick's drive letter):
      .\tools\sync-usb.ps1 -Drive E -Apply
3. Create  audit.conf  in the USB root (contents in section C).
   The sync never copies or changes audit.conf - it holds this
   stick's passwords. (Plain Notepad is fine - the tools strip
   Windows line endings.)


---------------------------------------------------------------------
  C) audit.conf CONTENTS   (fill in your own details)
---------------------------------------------------------------------
A plain text file named exactly "audit.conf" in the USB root.
Use straight quotes ("), no spaces around the = sign.
tools\audit.conf.example has every setting with a full explanation;
the ones that matter:

   AUDIT_URL="https://als-inventory-software-production.up.railway.app"

   # A DEDICATED STATION ACCOUNT - never a person's login, NEVER an admin.
   # This sits in plain text on a stick in a warehouse. Create it in ALS
   # Inventory under Users -> New User: role Technician, untick everything,
   # then tick only Goods In, Perform Amazon Audit, Perform Goods In Audit.
   AUDIT_EMAIL="station@YOUR_DOMAIN"
   AUDIT_PASSWORD="FROM_YOUR_PASSWORD_MANAGER"

   # Who did the wipe. Default (setting absent or "0"): operators type
   # their name on the kiosk and wipes are filed with the station
   # account above; the certificate prints the name as self-declared.
   # AUDIT_OPERATOR_SIGNIN="1": nobody can wipe, audit or restore until
   # someone signs in ON THE SCREEN with their own ALS login. Signing in
   # needs the network (there is no offline sign-in). Each record is
   # filed under that person's own account; a record made offline waits
   # on the stick and is sent only when THAT person signs in again. The
   # station account is then never used. Leave it off until you have run
   # HARDWARE-TESTS.md Test 4 on the station.
   AUDIT_OPERATOR_SIGNIN="0"

   # Admin PIN for the kiosk's Settings screen. WITHOUT one, the server
   # address, image server and wipe method cannot be changed from the
   # screen at all (Wi-Fi still can). Pick a PIN, keep it off the stick label.
   AUDIT_ADMIN_PIN="YOUR_PIN"

   # Wi-Fi to connect to at the start of each run (blank = use Ethernet)
   WIFI_SSID="YOUR_WIFI_NAME"
   WIFI_PASSWORD="YOUR_WIFI_PASSWORD"

   # Method the kiosk pre-selects for a wipe:
   #   auto | crypto | secure | overwrite | zero   (see bottom)
   AUDIT_WIPE_METHOD="auto"
   # Try to unfreeze SATA drives via suspend/resume:  0 = off, 1 = on
   # (leave 0 - some machines never resume)
   AUDIT_WIPE_UNFREEZE="0"

AUDIT_WIPE IS RETIRED. It used to switch on a wipe in the text-mode
script that erased every drive and filed them all as ONE result. It
now erases nothing whatever it is set to - the text-mode script only
prints that wiping is done from the kiosk screen. Delete the
AUDIT_WIPE line from old audit.conf files (leaving it is harmless).


---------------------------------------------------------------------
  D) SET UP AUTO-RUN   (OLD SystemRescue stick, reference only)
---------------------------------------------------------------------
SystemRescue runs scripts inside an "autorun" FOLDER at the USB root.
Boot the machine off the USB to the  [root@sysrescue ~]#  prompt, then
type these ONE AT A TIME (press Enter after each):

   mount -o remount,rw /run/archiso/bootmnt
   mkdir -p /run/archiso/bootmnt/autorun
   printf '#!/bin/bash\nexec bash /run/archiso/bootmnt/hardware-audit.sh\n' > /run/archiso/bootmnt/autorun/autorun

Check it worked (should print two lines starting with #!/bin/bash):

   cat /run/archiso/bootmnt/autorun/autorun

IMPORTANT: the ">" in the printf line is REQUIRED (it writes the file).
Type it exactly. No spaces inside the /paths.

(The Ubuntu stick has no autorun: the kiosk starts from its own boot
session once the layer is built and armed - section H.)


---------------------------------------------------------------------
  E) DATA WIPE   (DESTRUCTIVE - kiosk screen only)
---------------------------------------------------------------------
Wiping is done ON THE KIOSK SCREEN, and nowhere else. There is no
switch to turn on in audit.conf any more.

1. Let the kiosk read the machine first. It will not start a wipe
   without this machine's captured hardware profile (or while it is
   still reading). If it says so, press Rescan (top right of the
   screen) and wait.
2. Pick the drive(s) and the method, check the drive's size and model
   (and serial, where the screen shows it), and confirm. Several
   drives can be picked at once, but each is its own job with its own
   result and its OWN record - never one merged result.
3. Before anything is written, the drive is checked against the
   capture:
     - only internal, fixed drives are offered: never USB, never
       removable, never the stick you booted from;
     - a drive whose serial was NOT in the captured profile is refused
       (it may have been plugged in or swapped since) - press Rescan;
     - the engine re-reads the drive's own serial and refuses if it is
       not the drive you picked;
     - a drive that reports NO serial is allowed; its record carries
       no drive serial (identity unknown), and the certificate lists
       it as "serial not reported by the drive".
     - SATA drives are checked for hidden areas (HPA / DCO) first. An
       HPA is removed until the next power cycle; if it cannot be, or a
       DCO is present, the drive FAILS (the station never runs
       --dco-restore). If it cannot be checked at all (RAID / RST
       controllers) the wipe goes ahead with that noted on the record.
4. Each drive ends with ONE of three results:

   WIPED    the erase ran AND the drive was read back afterwards with
            none of its old data recognisable (see WIPE METHODS at the
            bottom). There is no result for "the drive said it worked".
            A wipe record is filed for that drive (serial, model, method
            asked for and achieved, level Purge/Clear, read-back
            verdict, limitations, start/finish time, tool version).
   FAILED   the erase did not complete, OR the read-back found old
            data, OR the read-back could not be done at all (an erase
            nobody could check is never recorded as wiped). Also a job
            that died with no result. A FAILED record is filed, with
            the reason. Treat the drive as still holding data and wipe
            it again before it can be resold.
   REFUSED  NOTHING was written to the drive (wrong drive, USB,
            removable, boot disk, not a real disk). NOTHING is
            recorded either.

   No network? The wipe still completes; the record is kept on the
   stick and uploads by itself later, with the real wipe time.

WIPE EVERY INTERNAL DRIVE of the machine. The certificate covers the
whole machine and the server works it out PER DRIVE: it is issued only
when every internal drive in the wipe-time hardware profile has a WIPED
record (a drive's latest record counts, so a failed drive wiped again
is fine). While any drive is failed or has no wipe, the asset shows
"data wipe failed", there is no certificate, and the kiosk's summary
names the drive holding it up. One certificate lists every drive with
its own serial, method and result.

Older records (from a stick before per-drive records) are still
certified, labelled "Drive not individually recorded (record predates
per-drive tracking)" and dated "Date recorded". For a machine with only
such records the old rule still applies: no certificate while a FAILED
wipe record is newer than its WIPED record, or less than 24 hours older
than it. An old certificate downloaded again keeps its number but has
the new wording - expected.

Test on a sacrificial drive first after any change to the stick.


---------------------------------------------------------------------
  F) RUN IT
---------------------------------------------------------------------
Ubuntu stick: boot it; with the layer built and armed (section H) the
   kiosk comes up by itself. Without the layer, from the live session:
      bash /cdrom/gui/start-gui.sh        (the kiosk - NOT with sudo)
      sudo bash /cdrom/hardware-audit.sh  (text mode - audit only)

See what it captures WITHOUT uploading or wiping (safe test):
   sudo env AUDIT_DEBUG=1 bash /cdrom/hardware-audit.sh

Old SystemRescue stick: it ran on its own at boot, or by hand with
   bash /run/archiso/bootmnt/hardware-audit.sh


---------------------------------------------------------------------
  G) UPDATING THE SCRIPT LATER
---------------------------------------------------------------------
Ubuntu stick: run the sync from section B again. The kiosk and the
engine are read from the stick at every boot, so a sync is all they
need - no layer rebuild.

Old SystemRescue stick: copy the new hardware-audit.sh over the old
one in the USB root. To make the USB writable first (needed after
every boot):

   mount -o remount,rw /run/archiso/bootmnt


---------------------------------------------------------------------
  H) UBUNTU STICK: REBUILD THE LAYER ONCE (Firefox ESR, snapd off)
---------------------------------------------------------------------
The stick boots through a layer file,
   casper\minimal.standard.live.als.squashfs
built ON the station by make-als-layer.sh. The September 2026 boot
changes live INSIDE that layer, so it has to be rebuilt ONCE:
  - bakes in Mozilla's Firefox ESR (key fingerprint checked; the build
    STOPS if it does not match 35BAA0B33E9EB396F59CA838C0BA5CE6DC6315A3),
  - turns snapd off in the layer - ONLY when ESR really went in, ALL of it
    (a half-finished unpack, e.g. the stick ran out of RAM space, is
    removed again and snapd is left on) - so the
    ~1.4 GB of snaps are no longer copied into RAM on every boot (~95 s),
  - stops ldconfig & co. re-running on every boot (~8 s),
  - switches cloud-init off (the file /etc/cloud/cloud-init.disabled in
    the layer; the kiosk never uses it, and the desktop waited on it),
  - packs the layer with lz4 instead of xz, ONLY when the stick's own
    casper/vmlinuz is the proven 24.04.2 kernel (Firefox started in
    6.7 s from xz, 1.8 s from lz4, measured off the station; the layer
    grows to about 160 MB). Anything else: xz, as before, and it says why,
  - ships a ready-made Firefox profile, so the kiosk's Firefox skips its
    first-run work on every boot (1.8 s -> 1.05 s, measured).

1. On Windows: sync the stick (section B), so it has the current
   make-als-layer.sh.
2. On Windows: COPY  E:\casper\minimal.standard.live.als.squashfs  to a
   folder on the PC. The build overwrites it and keeps no backup.
3. Boot the stick on a station machine WITH INTERNET. From the live
   session open a terminal and type:

      sudo bash /cdrom/make-als-layer.sh build --with-session

   Read the end of the output:
     "firefox-esr baked in" and "masked: snapd..." and
     "cloud-init: switched off (/etc/cloud/cloud-init.disabled)"
          = the full change went in.
     "ESR skipped, snapd left alone"
          = no internet, or the download/key did not check out. The
            layer still boots exactly as before, just not faster.
            Fix the cause and build again. If the MOZILLA KEY did not
            match, do NOT work around it (see UBUNTU-STICK.md).
     an error BEFORE the "Copying onto the stick" step
          = the build stopped; the stick is untouched.
     "copy failed"
          = the exception: it fails DURING that copy, which overwrites
            the layer on the stick in place. The layer is now DAMAGED
            and the stick is still armed, so it would not boot. Do NOT
            boot the stick again until you have copied the layer saved
            in step 2 back from Windows (see "To go back"). Usual
            cause: the stick is full - the new layer is bigger.
4. Check, then reboot:

      sudo bash /cdrom/make-als-layer.sh status

   "ALS layer" should show a size and "armed" should say yes. The
   build does not touch grub.cfg, so an armed stick stays armed. If
   "armed" says no:   sudo bash /cdrom/make-als-layer.sh arm
   Reboot and check the kiosk comes up.

Do this ONCE. Rebuild again only when make-als-layer.sh or its
package list changes.

To go back, any one of:
   copy the layer you saved in step 2 back over
      E:\casper\minimal.standard.live.als.squashfs  from Windows
      (the layer file is the whole change)
   sudo env ALS_ESR=0 bash /cdrom/make-als-layer.sh build --with-session
   (ALS_LAYER_COMP=xz after env: xz as before; ALS_FF_SEED=0: no
   ready-made Firefox profile)
      (no ESR, snapd left alone; add ALS_UPDATE_STAMPS=0 to also drop
       the ldconfig stamps, and ALS_CLOUD_INIT=1 to keep cloud-init on)
   sudo bash /cdrom/make-als-layer.sh undo
      (removes the layer entirely and un-arms grub.cfg: plain Ubuntu,
       no kiosk session, until you build and arm again)


---------------------------------------------------------------------
  WIPE METHODS (AUDIT_WIPE_METHOD = what the kiosk pre-selects)
---------------------------------------------------------------------
   crypto    = cryptographic erase - destroys the drive's encryption
               key (NVMe sanitize crypto erase or format -s2; enhanced
               ATA secure erase on SATA). NIST 800-88 "Purge".
   secure    = firmware erase (NVMe block-erase sanitize or format -s1;
               ATA secure erase on SATA).
   auto      = crypto -> secure -> overwrite (best the drive supports).
   overwrite = random pass + zero pass, read back. NIST "Clear".
   zero      = single zero pass, read back. NIST "Clear", half the time.

NVMe: the SANITIZE is tried first (crypto erase, then block erase);
"nvme format" only last, and only when it covers the whole drive. A
sanitize erases EVERY namespace of the drive, ticked or not (the
confirm dialog says so when a drive has more than one).

Level on the record: PURGE for an NVMe sanitize/format or an ENHANCED
ATA erase; CLEAR for an overwrite or a normal ATA erase. On flash an
overwrite reaches only the blocks the system can address, and a drive
with reallocated/pending sectors gets a limitation naming the counts -
both are printed on the record. If a stronger method was asked for
and not used, the record says what was asked for, what was done, and
why (e.g. the drive is frozen by the BIOS).

A frozen SATA drive (the BIOS usually freezes them) cannot take a
firmware erase and is overwritten instead. There is no TRIM step - TRIM
is not an erase.

Every wipe ends with a READ-BACK of the drive: first and last MiB,
eight windows across it, and every place a partition started before
the erase. The verdict is one of three:
   CLEAN       nothing of the old data. After an overwrite only zeros
               count. After a firmware erase: zeros, all 0xFF, a short
               repeated fill, or random-looking data (what a crypto
               erase leaves). The method ends "- verified (reads as
               ...)".  -> WIPED
   FOUND       a boot sector, partition table, or NTFS / BitLocker /
               FAT / LUKS / ext signature is still there (or, after an
               overwrite, anything but zeros). After a firmware erase
               the drive said "done" and did not erase: the station
               falls back to a full overwrite and reads THAT back.
               After an overwrite: FAILED.
   UNVERIFIED  the drive could not be read back (read error, drive
               gone, no python3). -> FAILED, with the reason.
The exact method is recorded on the device's audit and its
data-erasure certificate.

Check a drive's firmware-erase support (read-only, erases nothing):
   nvme id-ctrl /dev/nvme0 -H | grep -i crypto
   nvme id-ctrl /dev/nvme0 -H | grep -i sanitize
   nvme list-ns /dev/nvme0 --all        (how many namespaces)
